# Contrato de distintivos badgeSet v1 — implementação experimental

Data: 13/11/2026. Branch verificada: `experiment/hls-chat-lgc3-15min`.

Implementado `badgeSet.version: 1` como extensão aditiva da mensagem normalizada. Legado e v2 permanecem separados, com estados estruturais, índice original e validade por campo. Não há seleção visual, ordenação, combinação, deduplicação de badges ou carregamento de imagens.

**Validação:** 78 testes experimentais e 23 unitários da raiz passaram. O caminho dos módulos reais até a resposta Luna foi testado com infraestrutura simulada. O consumidor atual aceitou a amostra serializada no Chromium e produziu DOM e pixels idênticos aos do contrato anterior. Não houve observação WSS, acesso a canais reais, instalação ou execução na TV.

## B. Contrato final

`badgeSet` sempre existe nas mensagens válidas produzidas por este normalizador; eventos de exclusão/moderação continuam com o formato anterior e sem esse acréscimo. O versionamento pertence somente ao novo contrato, sem alterar o envelope Luna ou a versão da sessão.

Cada fonte contém `{state, items, rejected, truncated}`:

| state | Significado |
|---|---|
| `absent` | A identidade não contém a chave da fonte, ou não há identidade objeto |
| `invalid` | A chave existe, mas seu valor não é array, inclusive null |
| `empty` | Array válido de comprimento zero |
| `items` | Array original não vazio, mesmo que todos os itens examinados tenham sido rejeitados |

`rejected` conta somente posições examinadas que não contêm objeto válido, incluindo null, arrays, primitivas e lacunas. Objetos com campos inválidos permanecem como registros com estados explícitos, permitindo degradação por campo. `truncated` informa que parte do array não foi examinada por atingir limite de posições ou de itens retidos. Fonte `items` com `items:[]` não equivale a array original vazio.

## C. Validação e limites

Os valores não utilizáveis são `null`; a razão estrutural fica em `fields`:

- `absent`: chave ausente;
- `invalid`: chave presente com tipo, tamanho ou estrutura rejeitados, inclusive null;
- `valid`: campo utilizável segundo sua validação estrutural;
- `known`/`unknown`: substituem valid para discriminadores de categoria, distinguindo valor reconhecido de string limitada não reconhecida.

| Campo | Política implementada |
|---|---|
| Fonte | Até 16 posições examinadas e oito objetos retidos por array, independentemente da outra fonte. Nenhum limite visual de quatro |
| Legado `type` | String não vazia até 32 caracteres; correspondência exata com moderator, subscriber, sub_gifter, vip, og, broadcaster, founder, verified, staff, bot |
| Tipo desconhecido | `type:null`, `fields.type:unknown`; não copia o discriminador arbitrário nem o reconhece como nova categoria. Tamanho excessivo/tipo errado produz invalid |
| Legado `text` | String não vazia até 40 caracteres antes do saneamento; controles C0/DEL e controles direcionais U+202A–U+202E/U+2066–U+2069 removidos; resultado vazio é inválido. Não é chave de categoria |
| Legado `count` | Apenas inteiro seguro não negativo, inclusive zero, até Number.MAX_SAFE_INTEGER. Sem coerção e sem unidade atribuída |
| v2 `name` | String não vazia até 64 caracteres, com o mesmo saneamento de controles. Preserva designação limitada sem usá-la como ID, escopo ou permissão |
| v2 `badge_type` | Somente global é reconhecido. Outras strings não vazias até 32 caracteres viram null/unknown, sem inventar canal |
| v2 `selected` | Booleano estrito. True e false preservados; ausente ou inválido gera null com estado distinto. False não é filtrado |
| v2 `sort_order` | Qualquer inteiro seguro, incluindo negativo e zero, entre Number.MIN_SAFE_INTEGER e Number.MAX_SAFE_INTEGER. Sem ordenação ou default zero |
| v2 `metadata` | Somente objeto não array; recebe estado próprio. Nenhuma cópia indiscriminada do objeto |
| `metadata.level` | Somente inteiro seguro não negativo, sem derivação de mês/duração. Se metadata está ausente, level é absent; se metadata é inválida, level é invalid |
| `active` e demais atributos extras | Não entram em v1. Active não foi observado nem necessário a esta entrega; não há default true |

As categorias moderator/subscriber/sub_gifter têm exemplos técnicos oficiais; a inclusão inicial das outras sete deriva das fontes independentes registradas e, para algumas, da ocorrência literal. A lista não constitui inferência de autorização ou enum completo da Kick. Alterá-la exige mudança explícita/testada de código, sem descoberta dinâmica.

Strings excessivas são rejeitadas por campo, não truncadas para criar uma chave diferente. HTML em rótulos permanece texto inerte; o módulo não cria DOM nem interpreta markup. Campos desconhecidos não são copiados. Não existe dependência entre este módulo e a UI.

### Referência de imagem inerte

[exemplo de metadados omitido] admite string ASCII até 1.024 caracteres, com autoridade absoluta HTTPS e hostname válidos segundo URL. Rejeita whitespace/controles, barras invertidas, credenciais (inclusive autoridade com @ vazio), porta não padrão, query e fragmento. A restrição adicional de query/fragmento evita transportar referências com parâmetros que possam carregar credenciais, até existir uma política própria para isso. Porta padrão 443 explícita é aceita. O valor original válido é preservado, sem construir ou reescrever caminhos.

**Valid não significa origem confiável.** Uma URL sintática de host desconhecido pode viajar como dado inerte; ela não é passada para img, CSS, fetch, cache ou downloader. A futura apresentação exigirá outra política de origem/caminho, conteúdo, tamanho e redirecionamento. Esta entrega não acessa essas referências, não confirma MIME/animação/disponibilidade e não prova que são assets oficiais.

### Compatibilidade e custo

O campo anterior `badges` continua exatamente com seu mapeamento limitado de type/text (oito posições iniciais, 32/40 caracteres), para consumidores anteriores. Esse campo legado não recebeu a nova classificação: pode conter um discriminador desconhecido limitado como já ocorria. A política de null/unknown pertence a `badgeSet`; novos recursos devem usar o contrato versionado. Não há promoção desse conteúdo antigo à lista reconhecida.

Isso mantém uma pequena projeção compatível no serviço, sem duplicar metadados no cliente: a UI descarta ambos os campos que não usa. Em uma migração futura, a remoção de `badges` precisa de decisão separada; não foi feita aqui.

O contrato sem fontes ocupa 149 bytes JSON UTF-8; o exemplo com um legado e um v2 ocupa 561 bytes. Testes com os oito itens máximos de cada fonte, strings/URLs máximas, inteiros extremos e rótulos Unicode com escape verificam badgeSet abaixo de 20 KiB JSON por mensagem. É um teto de fixture/serialização, não medição de heap da LG ou garantia de limite do barramento Luna. Mensagens de dados máximos em lotes ainda exigem avaliação no dispositivo. Permanecem fila de serviço cinco, lote até 500 ms, fila UI 20, DOM 60 e deduplicação de mensagens com 200 IDs.
